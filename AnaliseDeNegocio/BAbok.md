# Dinâmica de Engenharia de Requisitos — Sistema de Gestão de Projetos Ágil

## 1. Cenário

**Contexto:**
Startup de tecnologia em fase de crescimento, com aumento no número de projetos, clientes e colaboradores. A empresa enfrenta problemas relacionados à organização, comunicação, acompanhamento de tarefas e cumprimento de prazos.

**Missão da equipe:**
Projetar um **Sistema de Gestão de Projetos Ágil** capaz de eliminar o caos operacional, centralizando informações, organizando tarefas e melhorando a comunicação entre as equipes.

**Referência:**
BABOK — *Business Analysis Body of Knowledge*.

---

# 2. Planejamento e Monitoramento da Análise de Negócios

### Objetivo

Definir como a análise de negócios será realizada, acompanhada e controlada durante o projeto.

### Atividades

* Identificar os principais stakeholders.
* Definir os objetivos da análise.
* Definir métodos de elicitação.
* Estabelecer prioridades para os requisitos.
* Definir como será realizada a comunicação.
* Criar um cronograma para levantamento e validação dos requisitos.
* Definir indicadores para acompanhar o andamento da análise.

### Stakeholders

* CEO da startup
* Gerentes de projeto
* Product Owner
* Desenvolvedores
* Designers/UX
* Equipe de QA
* Clientes
* Usuários finais

### Objetivo de negócio

> Reduzir atrasos, falhas de comunicação e falta de visibilidade dos projetos por meio de um sistema centralizado de gestão ágil.

---

# 3. Elicitação e Colaboração

### Objetivo

Identificar as necessidades, expectativas, problemas e requisitos dos stakeholders.

### Técnicas de elicitação

#### Entrevistas

Conversar com gerentes, desenvolvedores e usuários para identificar os principais problemas enfrentados atualmente.

#### Brainstorming

Reunir a equipe para levantar possíveis funcionalidades e soluções.

#### Questionários

Coletar opiniões de um número maior de colaboradores e usuários.

#### Observação

Observar como os projetos são atualmente planejados, executados e acompanhados.

#### Workshops

Reunir diferentes áreas da empresa para discutir problemas e possíveis soluções.

### Perguntas para elicitação

* Como os projetos são controlados atualmente?
* Quais são os principais problemas?
* Onde as informações ficam armazenadas?
* Como as tarefas são distribuídas?
* Como os gestores acompanham os projetos?
* Como são identificados os atrasos?
* Como ocorre a comunicação entre as equipes?
* Quais informações os clientes precisam acompanhar?

---

# 4. Análise Cooperativa

### Objetivo

Trabalhar em conjunto com os stakeholders para compreender os problemas, analisar alternativas e chegar a uma solução de consenso.

### Problemas identificados

| Problema                          | Impacto                                          |
| --------------------------------- | ------------------------------------------------ |
| Falta de organização das tarefas  | Atrasos                                          |
| Informações espalhadas            | Perda de produtividade                           |
| Falha na comunicação              | Erros e retrabalho                               |
| Falta de acompanhamento           | Projetos atrasados                               |
| Falta de definição de prioridades | Equipes trabalhando em tarefas menos importantes |
| Ausência de indicadores           | Gestores sem visão do projeto                    |

### Soluções discutidas

* Quadro Kanban.
* Dashboard de projetos.
* Controle de tarefas.
* Definição de responsáveis.
* Sistema de prioridades.
* Notificações.
* Controle de prazos.
* Relatórios de desempenho.
* Comunicação centralizada dentro do projeto.

### Resultado esperado

Chegar a um consenso entre os stakeholders sobre:

1. Quais problemas são mais críticos.
2. Quais funcionalidades devem ser desenvolvidas primeiro.
3. Quais necessidades geram maior valor para o negócio.

# 5. Análise de Requisitos

### Objetivo

Transformar as necessidades identificadas em requisitos claros, estruturados, priorizados e verificáveis.

## Requisitos Funcionais

### RF01 — Cadastro de usuários

> O sistema deve permitir o cadastro de usuários.

### RF02 — Criação de projetos

> O sistema deve permitir que usuários autorizados criem novos projetos.

### RF03 — Gerenciamento de tarefas

> O sistema deve permitir criar, editar, excluir e atribuir tarefas.

### RF04 — Quadro Kanban

> O sistema deve permitir visualizar e movimentar tarefas por meio de um quadro Kanban.

### RF05 — Definição de responsáveis

> O sistema deve permitir definir um responsável para cada tarefa.

### RF06 — Controle de prazos

> O sistema deve permitir estabelecer prazos para as tarefas.

### RF07 — Priorização

> O sistema deve permitir classificar tarefas de acordo com sua prioridade.

### RF08 — Notificações

> O sistema deve notificar os usuários sobre alterações, prazos e tarefas atribuídas.

### RF09 — Dashboard

> O sistema deve apresentar indicadores sobre o andamento dos projetos.

### RF10 — Relatórios

> O sistema deve permitir gerar relatórios sobre o desempenho dos projetos.

---

## Requisitos Não Funcionais

### RNF01 — Desempenho

> O sistema deve responder às principais operações em até 2 segundos.

### RNF02 — Segurança

> O sistema deve utilizar autenticação para controlar o acesso dos usuários.

### RNF03 — Disponibilidade

> O sistema deve apresentar alta disponibilidade durante o horário de operação da empresa.

### RNF04 — Usabilidade

> O sistema deve possuir uma interface simples e intuitiva.

---

# 6. Competências Fundamentais

### Objetivo

Aplicar competências necessárias para realizar uma análise de negócios eficiente e tomar decisões durante o projeto.

### Pensamento analítico

Identificar as causas dos problemas e não apenas seus sintomas.

**Exemplo:**

> Problema: projetos atrasados.

A equipe deve investigar as causas:

* Tarefas sem responsáveis.
* Prioridades confusas.
* Falta de comunicação.
* Ausência de acompanhamento.
* Falta de definição de prazos.

### Comunicação

Traduzir as necessidades dos stakeholders para uma linguagem compreensível pela equipe técnica.

### Resolução de problemas

Comparar diferentes alternativas e selecionar a solução que melhor atende aos objetivos do negócio.

### Pensamento sistêmico

Compreender como as mudanças em uma área podem afetar outras partes da organização.

### Colaboração

Promover a participação dos diferentes stakeholders na definição da solução.

### Comportamento ético

Garantir que informações dos usuários, clientes e projetos sejam tratadas de maneira adequada e segura.

# 7. Avaliação e Validação da Solução

### Objetivo

Verificar se a solução proposta realmente atende às necessidades do negócio e resolve os problemas identificados.

### Pergunta principal

> **O sistema proposto realmente elimina o caos operacional da startup?**

## Situação atual

* Tarefas espalhadas.
* Comunicação descentralizada.
* Pouca visibilidade dos projetos.
* Atrasos frequentes.
* Dificuldade de acompanhamento.
* Falta de prioridades claras.

## Situação esperada

* Tarefas centralizadas.
* Responsáveis definidos.
* Prioridades claras.
* Acompanhamento em tempo real.
* Dashboard de projetos.
* Notificações automáticas.
* Comunicação centralizada.

### Validação com os stakeholders

Apresentar um protótipo ou fluxo do sistema e verificar:

* A solução atende às necessidades?
* Existe alguma funcionalidade importante faltando?
* A interface é compreensível?
* O fluxo de trabalho faz sentido?
* As prioridades estão corretas?
* O sistema realmente resolve os problemas identificados?

### Critérios de sucesso

* Redução dos atrasos dos projetos.
* Redução de tarefas esquecidas.
* Melhoria na comunicação entre equipes.
* Aumento da visibilidade dos projetos.
* Redução do tempo gasto pelos gestores no acompanhamento.
* Maior controle sobre prazos e responsabilidades.

# 8. Gerenciamento e Comunicação de Requisitos

### Objetivo

Garantir que os requisitos sejam documentados, rastreados, comunicados e controlados durante todo o projeto.

## Documentação dos requisitos

Cada requisito deve possuir:

* ID;
* Descrição;
* Prioridade;
* Origem;
* Responsável;
* Status;
* Critérios de aceitação.

### Matriz de requisitos

| ID   | Requisito            | Prioridade | Status     |
| ---- | -------------------- | ---------- | ---------- |
| RF01 | Cadastro de usuários | Alta       | Aprovado   |
| RF02 | Criar projetos       | Alta       | Aprovado   |
| RF03 | Gerenciar tarefas    | Alta       | Aprovado   |
| RF04 | Quadro Kanban        | Alta       | Em análise |
| RF05 | Notificações         | Média      | Em análise |
| RF06 | Dashboard            | Média      | Proposto   |

# 9. Gerenciamento de Mudanças

Durante a dinâmica, pode ser introduzida uma nova necessidade para simular um ambiente de alta pressão.

### Exemplo de mudança

> O CEO informa que os clientes também precisam acompanhar o andamento dos projetos.

### A equipe deve:

1. Registrar a nova necessidade.
2. Analisar o impacto da mudança.
3. Criar ou alterar os requisitos.
4. Avaliar impacto em custo, prazo e escopo.
5. Definir a prioridade.
6. Validar a mudança com os stakeholders.
7. Atualizar a documentação.
8. Comunicar a mudança à equipe.

# 10. Fluxo Completo da Dinâmica

```text
PLANEJAMENTO
     ↓
ELICITAÇÃO
     ↓
ANÁLISE COOPERATIVA
     ↓
ANÁLISE DE REQUISITOS
     ↓
COMPETÊNCIAS FUNDAMENTAIS
     ↓
AVALIAÇÃO E VALIDAÇÃO
     ↓
GERENCIAMENTO E COMUNICAÇÃO
     ↓
NOVA NECESSIDADE / MUDANÇA
     ↓
ANÁLISE DE IMPACTO
     ↓
ELICITAÇÃO E REVISÃO
     ↓
VALIDAÇÃO
```

#O processo deve ser entendido como **cíclico**, e não como uma sequência que termina após a primeira validação.
